# SemVer + Releases + Changelog — Plan

## Goal

Introduce a repo-wide release workflow based on Semantic Versioning, git tags, and GitHub Releases, with a maintained `CHANGELOG.md` that follows Keep a Changelog conventions.

## Scope decisions

| # | Decision |
|---|---|
| 1 | Use one canonical product version for the repo and align package versions to it. |
| 2 | Adopt SemVer tags in the form `vX.Y.Z`. |
| 3 | Automate version bumps, release PRs, tags, and GitHub Releases from commit history. |
| 4 | Keep `CHANGELOG.md` human-readable and release-oriented, not an autogenerated dump. |
| 5 | Preserve existing deployment/build version identifiers that are unrelated to release versioning. |

## Strategy

1. Map the current versioning surface: root package state, package-lock metadata, release gaps, and any existing version endpoints.
2. Add the release automation configuration and the version files it needs.
3. Seed the baseline release state so the first tagged release starts from the current project version.
4. Define commit and changelog conventions so future releases stay predictable.
5. Verify the workflow locally and document the release process clearly in the repo.

## Implementation outline

### Version source of truth

- Add or standardize a root-level package manifest if needed for release tooling.
- Keep package versions in `api/` and `app/` synchronized with the repo release version.
- Update lockfile metadata when the release version changes so the workspace stays consistent.

### Release automation

- Use GitHub-native release automation that can:
  - create release PRs,
  - bump SemVer based on commit messages,
  - create annotated tags,
  - publish GitHub Releases.
- Configure repository permissions and workflow triggers so the automation can write tags/releases safely.
- Ensure release generation does not conflict with normal CI or deployment workflows.

### Changelog

- Add `CHANGELOG.md` at the repo root.
- Follow Keep a Changelog structure:
  - `## [Unreleased]`
  - `## [X.Y.Z] - YYYY-MM-DD`
  - `Added`, `Changed`, `Fixed`, `Removed`
- Make release notes concise, user-facing, and grouped by meaningful change.

### Tagging and publishing

- Start tagging releases with `vX.Y.Z`.
- Ensure the release process pushes tags to the remote and publishes corresponding GitHub Releases.
- Keep the first release consistent with the existing baseline version so history is clean.

## Risks / mitigations

- **Version drift** between root/package manifests and generated release metadata. Mitigate by making one release source authoritative.
- **Tag collisions** if an existing release version is assumed incorrectly. Mitigate by seeding the baseline before enabling automation.
- **Changelog noise** if release notes are fully machine-generated. Mitigate by keeping the changelog curated and release-oriented.

## Acceptance criteria

- A SemVer-based release workflow exists and is documented.
- Releases produce git tags and GitHub Releases automatically.
- `CHANGELOG.md` exists and follows Keep a Changelog conventions.
- Package versioning is aligned with the project release version.
- Existing build/runtime version identifiers are left intact where they serve a different purpose.

## Verification

- Confirm the release automation config is present and wired to the repo default branch.
- Confirm the changelog structure matches Keep a Changelog.
- Confirm the version files that should change are explicitly identified.
- Confirm the release workflow can publish tags and GitHub Releases without manual release-note assembly.
